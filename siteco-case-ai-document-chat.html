Build a Document Chat
Upload, retrieve, converse. Your frontend, your backend.

Key Take-away

01

The Assignment

Build a working AI chat application in which a user uploads documents and then asks questions about them. Retrieval-augmented generation is the expected pattern. How you implement retrieval is entirely your call.

1

Upload

User adds one or more documents through your interface.

2

Process

Backend parses, chunks, embeds and indexes the content.

3

Retrieve

A question pulls the passages that actually matter.

4

Answer

Model responds in chat, grounded in the uploaded document.

02

Scope and Technology Choices

Two components: a frontend and a backend. Everything inside them is your decision. We care about the reasoning behind each choice far more than the choice itself.

03

Ground Rules

Encouraged
  • AI coding assistants: use them as much as you can. We work this way and expect you to.
  • Component libraries and pre-built UI blocks. Examples, not requirements: shadcn/ui, MUI, Mantine, Chakra, Tailwind kits. Anything equivalent is equally welcome.
  • Framework scaffolding and starters, established RAG libraries, any vector store.
  • Shortcuts you can justify. Deliberate simplification is a skill, not a gap.
Not in scope
  • Forking a finished chat product, for example LibreChat, Open WebUI, AnythingLLM or comparable ready-made applications.
  • Any drop-in that ships the chat UI and the RAG backend pre-assembled.

The frontend and the backend must be your build. Everything underneath that line is fair game.

04

Deliverables

What you hand over

  • GitHub repository with full source and commit history intact.
  • Container setup so the application starts on our machine via Docker. Name the required environment variables and keys.
  • README covering how to run it, what you built, which decisions you took and why, and what you would do next with more time.
  • Live demo, run locally from your machine during the call.

Optional, on top of a working baseline

  • Chat artifacts and rich rendering
  • Citation highlighting in the source document
  • Multi-model routing or side-by-side comparison
  • Retrieval evaluation with numbers attached
05

The Call, 30 Minutes

~10 min
DemoYou run the application end to end and walk us through it.
~20 min
Questions on frontend and backendArchitecture, trade-offs, what broke, what you would change.

How we evaluate

  • Decision quality: you can explain why, and name the option you rejected.
  • It works: the happy path runs on our machine, from the container.
  • Depth where it counts: the parts you went deepest on hold up under questioning.
  • Judgment on scope: you know what to leave out.
  • Readable code: structure, naming, boundaries.

Not evaluated: pixel-perfect design, exhaustive edge cases, production hardening.

Not everything has to be perfect.
Everything has to work.

We are looking for how you think, what you are genuinely strong at, and whether you can defend the decisions you made. Build the version of this you would be proud to explain.
